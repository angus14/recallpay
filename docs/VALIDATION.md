# What still needs validation

## Closest building blocks reviewed

| Existing work | What exists | Proposed RecallPay contribution |
| --- | --- | --- |
| [OpenLineage](https://openlineage.io/docs/) | Dataset, job and run lineage metadata | Bind a paid version to a funded fee-refund obligation and the next permitted payment |
| [NEAR AI Agent Market](https://near.ai/blog/what-is-agent-market) | Job hiring, held payments, acceptance, refunds and disputes | Handle an input recalled after its purchase, including dependent jobs outside the original sale |
| [NEAR agentic payments](https://www.near.org/agentic-payments) | x402/MPP settlement and multichain payouts | Decide consequences for a paid resource version later recalled by its provider |

These comparisons are based on the linked public descriptions reviewed on
2 November 2026. They are not evidence that those products lack every similar
feature. Search results alone cannot establish a first-of-its-kind claim.

Novelty validation should next examine API SLA credits, data-product
deprecation/correction notifications, lineage incident tools, and x402
post-settlement refunds. Avoid claiming a new cryptographic primitive.

## Customer questions before expanding scope

Interview two paid data/API providers, two research-agent operators and one
marketplace integrator. No outreach has been sent by this project.

Ask for concrete recent examples, not general enthusiasm:

1. Describe the last paid data correction you issued or received. How were
   customers found, notified and reimbursed? How long did it take?
2. Which workflows continued using the old version? What did that cost?
3. Can you already identify a dataset version across downstream jobs?
4. Would a provider lock a matching reserve for each protected sale? Which
   duration and price would make that acceptable?
5. Would the buyer route its next paid action through a separate payment gate?
6. Could the existing provider issue a credit note more cheaply? What would
   justify using this product instead?

Record observed incidents, current workaround, required integration, acceptable
capital lockup, and willingness to run a small pilot. A useful validation result
is one provider and one buyer agreeing to a real workflow and its terms.

## Current evidence

- Implemented: one provider, two scripted buyers, synthetic versioned data,
  NEAR-native prefunded coverage, dependency-aware gate and fee refunds.
- Measured evidence is generated by `npm test` and `npm run demo`.
- Not established: production need, willingness to pay, adoption, worldwide
  novelty, production safety, or probability of a hackathon award.

## Next product milestone

Find one data API that publishes versioned corrections. Add an adapter for its
signed correction notice, reproduce a consented example, and let one independent
builder integrate the SDK. Keep the declared trust boundary visible.
